# Zhyguzyn 4.0

Android-застосунок для обліку пального в автомобілі: записує заправки, рахує середню
витрату методом «від повного бака до повного бака», показує залишок у баку та запас ходу,
а також оновлюється сам із GitHub Releases.

## Можливості

- **Головний екран** — залишок пального з індикатором бака, середня витрата
  (загальна та за останній інтервал), орієнтовний запас ходу.
- **Додати заправку** — пробіг з одометра, літри, позначка «повний бак», дата
  (за замовчуванням сьогодні).
- **Історія** — список заправок; натисніть на запис, щоб відредагувати, або на кошик,
  щоб видалити. Статистика перераховується автоматично.
- **Прикинути** — введіть поточний пробіг (або скільки проїхали) і одразу побачите,
  скільки приблизно пального в баку та на скільки км його вистачить. Нічого не зберігається.
- **Налаштування** — об’єм бака, початковий залишок, перевірка оновлень, версія.

### Як рахується

- **Середня витрата** = літри, залиті між двома заправками «до повного» (включно з другою),
  ÷ кілометри між ними × 100. Загальна середня — сума літрів усіх таких інтервалів ÷ сума
  кілометрів. Потрібно щонайменше дві заправки до повного бака, інакше застосунок
  показує пояснення замість нуля.
- **Залишок після останньої заправки** — рахується від останньої заправки до повного
  (бак = об’єм), а якщо таких ще не було — від початкового залишку з налаштувань.
  Між заправками пальне списується за середньою витратою. Значення завжди в межах
  від 0 до об’єму бака.
- **Поточний залишок** (екран «Прикинути») = залишок після останньої заправки −
  пробіг від неї × середня витрата ÷ 100.
- **Запас ходу** = залишок ÷ середня витрата × 100.
- **Лічильник, що обнуляється.** Якщо лічильник рахує до 999,9 км і починає з нуля,
  у налаштуваннях вкажіть «Лічильник обнуляється після» = `1000` (це значення за
  замовчуванням; `0` — звичайний одометр без обнулення). Тоді пробіг між заправками
  рахується з урахуванням переходу через нуль: 850 → 120 = 270 км. Заправки
  впорядковуються за датою, а в межах одного дня — за порядком введення.
  Між сусідніми заправками має бути менше 1000 км, інакше повний оберт лічильника
  неможливо помітити.

Уся логіка — у `app/src/main/java/com/kazum0ra/zhyguzyn/domain/` і покрита unit-тестами
(`app/src/test/...`).

## Технології

Kotlin, Jetpack Compose (Material 3), MVVM, Room, DataStore, Navigation Compose.
minSdk 26, targetSdk/compileSdk 37. Android Gradle Plugin 9, Gradle 9 (через wrapper).

## Збірка

Потрібні JDK 17+ (рекомендовано 21) і Android SDK (шлях у `ANDROID_HOME` або
`local.properties`).

```bash
./gradlew testDebugUnitTest   # unit-тести
./gradlew assembleRelease     # APK: app/build/outputs/apk/release/app-release.apk
```

Якщо ключ підпису не налаштовано, `assembleRelease` все одно збирає APK, але підписує
його **debug-ключем** (у лозі буде попередження). Такий APK підходить для перевірки,
але поверх версії з GitHub Releases він не встановиться — підписи різні.

Версія локальної збірки — `0.0.1`. Щоб зібрати конкретну версію:
`./gradlew assembleRelease -PappVersion=v1.2.3`.

## Свій репозиторій для оновлень

Застосунок перевіряє `https://api.github.com/repos/OWNER/REPO/releases/latest`.
OWNER/REPO задаються одним рядком у
`app/src/main/java/com/kazum0ra/zhyguzyn/AppConfig.kt`:

```kotlin
const val GITHUB_REPOSITORY = "KAZUM0RA/Zhyguzyn-4.0"
```

> Репозиторій має бути **публічним**: застосунок звертається до GitHub API без токена,
> а для приватного репозиторію GitHub відповідає 404 («релізів ще немає»).

Автоматична перевірка відбувається при запуску, не частіше ніж раз на добу; вручну —
кнопкою «Перевірити оновлення» в налаштуваннях. Якщо тег релізу (`v1.2.3`) новіший за
версію застосунку, з’явиться діалог зі списком змін і кнопкою «Оновити»: APK
завантажується через DownloadManager і відкривається системний інсталятор. Під час
першого оновлення Android попросить дозволити встановлення застосунків з цього джерела.

## Підпис і випуск версій

Усі версії **мають підписуватися одним і тим самим ключем** — інакше Android не
встановить оновлення поверх старої версії. Ключ генерується один раз і зберігається
надійно (менеджер паролів, резервна копія). Якщо ключ загубити, користувачам доведеться
видалити застосунок (разом з даними) і встановити заново.

### 1. Згенерувати keystore (один раз)

Потрібен `keytool` — він входить до JDK.

```bash
keytool -genkeypair -v \
  -keystore release.jks \
  -alias zhyguzyn \
  -keyalg RSA -keysize 4096 \
  -validity 10000
```

`keytool` запитає пароль сховища, ім’я тощо. Запам’ятайте:
пароль сховища (**KEYSTORE_PASSWORD**), alias (**KEY_ALIAS**, тут `zhyguzyn`) і пароль
ключа (**KEY_PASSWORD**; якщо `keytool` не питав окремо — він такий самий, як пароль сховища).

> Файл `release.jks` не можна комітити в репозиторій — `.gitignore` уже виключає `*.jks`.

### 2. Закодувати keystore у base64

Linux:

```bash
base64 -w 0 release.jks > release.jks.base64
```

macOS:

```bash
base64 -i release.jks -o release.jks.base64
```

Windows (PowerShell):

```powershell
[Convert]::ToBase64String([IO.File]::ReadAllBytes("release.jks")) | Set-Content release.jks.base64
```

### 3. Додати секрети в GitHub

Репозиторій → **Settings → Secrets and variables → Actions → New repository secret**:

| Секрет              | Значення                                    |
|---------------------|---------------------------------------------|
| `KEYSTORE_BASE64`   | увесь вміст файлу `release.jks.base64`      |
| `KEYSTORE_PASSWORD` | пароль сховища                              |
| `KEY_ALIAS`         | alias ключа (наприклад, `zhyguzyn`)         |
| `KEY_PASSWORD`      | пароль ключа                                |

Або через GitHub CLI:

```bash
gh secret set KEYSTORE_BASE64 < release.jks.base64
gh secret set KEYSTORE_PASSWORD
gh secret set KEY_ALIAS
gh secret set KEY_PASSWORD
```

Після цього файл `release.jks.base64` можна видалити.

### 4. Випустити нову версію

Версія (`versionName`) і `versionCode` беруться з тегу автоматично:
`v1.2.3` → versionName `1.2.3`, versionCode `1002003`
(major × 1 000 000 + minor × 1 000 + patch, тож minor і patch мають бути меншими за 1000).

Тег ставиться на останній коміт гілки з кодом:

```bash
git pull
git tag -a v1.0.0 -m "Що нового:
- перша версія"
git push origin v1.0.0
```

Або без git-команд: вкладка **Actions** → **Release** → **Run workflow** → вкажіть
версію (`v1.0.1`) і, за бажанням, опис змін. Тег створиться автоматично.

Workflow `.github/workflows/release.yml` запуститься сам: прожене unit-тести, збере
підписаний APK, перевірить підпис і створить GitHub Release `v1.0.0` з файлом
`zhyguzyn-v1.0.0.apk`. Текст анотованого тегу (`-m "..."`) стане описом релізу — саме
його застосунок покаже в діалозі оновлення. Якщо тег без опису, GitHub згенерує
нотатки з комітів.

Кожна наступна версія має мати більший номер: `v1.0.1`, `v1.1.0`, `v2.0.0`…
Хід збірки — на вкладці **Actions**, готовий реліз — у розділі **Releases**.

Якщо збірка впала і ви виправили проблему, видаліть тег і запуште його знову:

```bash
git tag -d v1.0.0
git push origin :refs/tags/v1.0.0
git tag -a v1.0.0 -m "..."
git push origin v1.0.0
```

### Збірка на кожен пуш

Workflow `.github/workflows/build.yml` на кожен пуш і pull request проганяє тести та
збирає APK. Його можна завантажити на вкладці **Actions** → потрібний запуск →
**Artifacts** → `zhyguzyn-apk`. Якщо секрети підпису задані, APK підписується релізним
ключем; якщо ні — тимчасовим debug-ключем (такий APK лише для перевірки, оновлюватися
з Releases він не зможе).

### Локальна збірка з релізним ключем (необов’язково)

Створіть у корені проєкту `keystore.properties` (він у `.gitignore`):

```properties
storeFile=release.jks
storePassword=...
keyAlias=zhyguzyn
keyPassword=...
```

Шлях `storeFile` — відносно кореня проєкту. Змінні середовища `KEYSTORE_FILE`,
`KEYSTORE_PASSWORD`, `KEY_ALIAS`, `KEY_PASSWORD` мають пріоритет над цим файлом.

## Перше встановлення на телефон

Завантажте `zhyguzyn-vX.Y.Z.apk` з розділу **Releases** на телефоні та відкрийте його.
Android попросить дозволити встановлення з браузера чи файлового менеджера — дозвольте.
Далі застосунок оновлюватиметься сам.
